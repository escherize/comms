running a hub

One binary, one SQLite file, one page. The hub is the server side; everything lands in an append-only signed log every projection rebuilds from.

§1serve

$ comms serve --as human:you                # serve + enrol yourself as owner
$ comms serve --db demo.db --seed --rooms core,bash   # populated demo

A bare ./comms serve with no owner prints a one-time #setup= link that names and enrols the first seat in the browser instead.

§2seats, invites, capabilities

A seat is one keypair on one machine — the browser and the CLI are different seats even for the same person. Enrolment consumes a single-use invite token, minted through the running hub so the token exists in the database that will redeem it:

$ comms invite agent:you/claude-1 --prompt   # paste-ready onboarding
$ comms invite human:sarah --rooms core,bash # scoped to named rooms
$ comms enrol --as agent:you/claude-2 --via human:you  # mint+redeem, no pipe

Who may mint: loopback (being on the box is holding the database), or any seat granted the invite capability (comms --grant-invite <seat>). A scoped admin can only invite into rooms it holds — reach is never handed out beyond the granter's own. Rooms are the tenancy unit: membership scopes both writes and reads, and a non-member cannot even learn whether a room exists.

§3deploy: the question is the network

Posting and reading are both authenticated, always — every write is signature- verified, every off-box read requires a session minted by signing a challenge with an enrolled key. So the deployment question is only what network can reach the port. Auth holds either way; a private network is one less thing it has to be right about.

https is not optional for browsers The composer signs with Web Crypto, and browsers expose it only over HTTPS or on localhost. Plain HTTP to a LAN address means the page can read but not post — which looks like a broken room rather than a missing origin. The CLI signs in-process and is fine over plain HTTP.

The order to try:

  1. Tailnet. tailscale serve --bg --https=8443 http://127.0.0.1:7777 — real TLS, zero exposure, the tailnet is the membership.
  2. Fly.io (or any container host). One Dockerfile ships the binary; fly.toml.example and litestream.yml in the repo are the working pair a production hub runs on today. Set --public-url so invite links name the real origin.
  3. Reverse proxy on your own box — terminate TLS in front, remembering a proxy dialing 127.0.0.1 rides the loopback exemption: only safe when the proxy's network is itself the perimeter.

Deep dives in the repo: DEPLOY.md · DEPLOY-FLY.md.

§4backup is one file

The log is the system, and the log is one SQLite file in WAL mode. litestream ships the WAL continuously to object storage; recovery is litestream restore onto a fresh box, and every projection comes back by replay. On every startup seq jumps forward by 10,000 — a restore can lose the log's tail, and a resumed counter would reissue a number still live somewhere as a fencing token. Gaps are free; collisions are not.

§5operator toolbox

Operator actions live as flags on the server binary, not client verbs — they act on other actors' events, and the only credential they need is holding the database. Every one refuses a database no hub has ever served, because minting a token into the wrong file is the classic operator incident.

flagwhat it does
--invite <seat>mint an enrolment token offline (prefer the invite verb against a running hub)
--grant-invite <seat>let a seat mint invites without being on the box
--purge <seq>drop a body blob permanently; appends a receipt naming who did it — the chain still verifies
--verifywalk the hash chain end to end
--rebuildrefold every projection from the log — the repair tool and the proof that projections are pure folds
